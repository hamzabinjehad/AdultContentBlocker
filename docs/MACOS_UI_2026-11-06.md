# Mac UI/UX — 6 November 2026

A window-and-sheet design pass, not a change to protection policy. It rebuilds
the Mac app's surface around one visual system and one order: the state first,
the evidence one click away, one decision per screen. This note records what
changed, what was observed, how it was checked and what it does not cover.

The pass is part of the current development line. It does not assign itself a
release number; version, changelog and store bookkeeping are recorded with the
rest of the current work.

## Why

Three problems, all visible in the 760-point window:

1. **Every control had the same weight.** System-grey cards with a hairline
   border held the status, the steps, the schedule and the tools. The answer to
   "am I protected?" sat beside a dozen equally loud explanations.
2. **The Setup page was a wall.** The first screen was a long checklist of raw
   text, with the next step, the diagnostic and the prose all competing. The
   network guide below it used yet another set of controls.
3. **The chrome repeated itself and lost its place.** The page name appeared in
   the toolbar, the window title and, on some pages, a heading. A page change
   could keep the previous scroll offset, and the pinned lock action used a
   faded accent instead of saying why it was unavailable.

## Design research

ScreenZen 2.0.0 (build 63) was already installed at `/Applications/ScreenZen.app`.
Its dashboard and its browser block page were opened and observed on 6 November
2026. What the interface made clear:

- one status or one figure leads a card; the sentence under it is short and
  observational, not a second paragraph;
- a single indigo accent carries selection, progress and the primary action;
  everything else is ink and muted grey;
- cards are large, soft and few, and the content column is centred rather than
  stretched;
- the block page asks one question ("Is this important?") and offers one calm
  next step, with the consequence beside the button.

The vocabulary taken was layout and tone: single-status-first, observation
cards, one decision per screen and a soft empty state. No ScreenZen code,
assets, icons, copy or data model was used, and the third-party capture is not
redistributed. This remains one observation of one installed build, not a
competitive benchmark.

The palette and type match the iPhone app's 1.7.0 surfaces, so the two devices
sound like one product. The Mac version keeps Mac conventions: a real title
bar, the system sidebar toggle, menu commands, keyboard shortcuts and native
text fields where a native field is the right control.

The new file `macos/Hisn/HisnTheme.swift` holds the palette, the rounded type
helpers, the canvas/card/ink-card surfaces, the page and section headers, the
buttons, the state badge, the layer ring, the notice, the toggle row, the text
field and the brand mark. Every state also has words and a symbol: the ring
writes its ratio, the layer chips write "Ready" / "Needs attention" / "Not set
up", and the notices carry an icon and a sentence.

## What changed

### The shell

- **Custom sidebar.** A shield mark and wordmark, five rows with an indigo
  selection pill and a hover state, the lock countdown beside Lock, and the
  persistent protection/lock card at the bottom. Native `List` selection
  followed the system accent (which can be graphite); this selection is part of
  the product's one accent and still exposes the `.isSelected` trait.
- **Page header.** Every page starts with its name and its one-line purpose at
  reading size. The toolbar no longer repeats them as a small subtitle.
- **Centred column.** Content is capped at 880 points and centred so a
  full-screen window keeps a readable measure.
- **Scroll reset.** The page content is keyed by page, so switching pages starts
  at the top. The previous shell could keep the old offset.
- **Toolbar.** Search and lock remain one click away. The lock action is hidden
  while the Lock page itself is open, so the page's own commitment bar is the
  only start button on that screen.
- **Accent.** The root view sets the indigo tint; switches, sliders, links and
  the sidebar selection inherit it.

### Overview

- The answer is one deep navy card: state badge, headline, one-line summary,
  a four-arc protection ring (one arc per layer), four layer chips, and one
  filled action. The button names what happens next from the real state:
  review setup, prevent private browsing, start a lock, or manage a lock.
- **Blocked connections today** moved out of the collapsed evidence and into
  the hero footer, still only when the filter itself reports a non-zero count
  for today. The filter still records no host, app, path or address.
- **Layer details** is a slim row that expands in place. Its content is the
  same evidence, now with a readable ratio and the "readiness is not proof"
  line.
- **Setup next step** carries a progress bar and the next stage, one click from
  Setup.
- **Lock** and **Tools** are quiet cards. Every warning is an inline notice
  under the status it qualifies; a lock with nothing enforcing it keeps the
  original honest warning.

### Protected Setup

- The status card, the ring and the readiness text share one header.
- Each of the four stages is a card with a calm header row: status, name, a
  "Next" badge, a done/total count and a rotating chevron. Only the open stage
  draws its steps.
- Steps are rows inside the stage card, not a card inside a card. Their actions
  are compact quiet buttons; the administrator command and the removal
  management guide stay disclosures.
- The account and recovery confirmations keep their exact consent text and
  their lock/management disabling rules.
- The network guide is now part of the same language: a section header, an
  information notice, one card for the router identity, one for the setup
  assistant, one for the instructions, and themed fields and buttons. It still
  configures nothing and still says that finding a router is not proof of
  blocking.

### Lock

- Length is a row of five choices (7 days, 30 days, 90 days, 1 year, Custom),
  with the custom amount and unit directly under it. The end date is a calm
  indigo band that names the chosen length and the wall-clock end.
- Two mode rows state what each switch means; the fixed-commitment sentence
  follows the switch instead of staying on screen when it is off.
- The administrator warning, the "I understand" acknowledgement, the daily
  schedule and the pinned action bar use the same cards and notices. The bar
  says which layers the lock would enforce, and its disabled state is neutral,
  not a faded accent.
- The running lock has its own deep card with the countdown, mode, progress and
  the started/ends pair, followed by "make it stronger", partner release and
  the slow early-release route.

### Blocking Rules

- The two site lists are separate cards with a themed add field and Add button,
  monospaced domain rows, a quiet remove control and the existing bulk paste.
- "Your words and apps" uses the same headers and fields. The words editor is a
  raised monospaced panel; the app picker and removal rules are unchanged.
- The browser-protection evidence is grouped into a raised inset panel; the
  read-only site checker and the browser-first guide stay one click from the
  lists.

### Settings

- Content checking is one card with a headed row for each switch, a sensitivity
  slider with a numeric badge, and a save row.
- Visual checks gets a heading and a reading order: what to open, what person
  blur estimates, and what the app cannot verify.
- The partner, gray screen, language and details sections keep their exact
  controls, now in the same cards, with the partner key field and buttons
  themed.
- Details keeps its monospaced values and the same freshness and failure
  warnings.

### First run, pause and sheets

- **Welcome** uses the same mark, headings, layer card and footer buttons, in
  English and Arabic.
- **Pause** is one deep navy surface in both system appearances: the mark,
  the breathing circle, one reminder, today's count and one close button.
  Closing is still immediate and nothing is recorded except the count.
- **Private-window consent**, **site check** and **connect-a-browser** use the
  same sheet headers, fields, notices and buttons. Their copy and their
  consent/refusal paths are unchanged.
- The menu-bar menu gained symbols on its actions; its state, pause count,
  blocked count and lock entry are unchanged.

## Verification

- **Tests.** `xcodebuild -scheme Hisn -configuration Debug test` — **580
  tests, 0 failures**. The new render tests check that every page lays
  out at 1120 points in light and dark, that Setup survives the minimum width
  with an injected checklist, that Overview and Lock mirror in Arabic, and that
  the welcome, private-window sheet and pause draw a non-trivial bitmap. They
  are layout captures, not pixel assertions.
- **Localization.** `xcodebuild -exportLocalizations` plus
  `macos/check_localization.py` reports **721 strings, all with Arabic**,
  including the new visible "Blocked connections today" label.
- **Review.** The captures in [`design/macos-ui-2026-11-06/`](../design/macos-ui-2026-11-06/README.md) were reviewed in
  light and dark, at 1120 and 760 points, and in Arabic right-to-left.

## Limits

- **No user study, task timing, screen-reader audit or physical-Mac acceptance.**
  The captures come from the test host. Native controls and the window chrome
  are composited by the system, so a control can look inactive in a capture
  where the test window was not key.
- **The Arabic capture is a layout check, not a copy check.** The test host sets
  SwiftUI's locale, not the app bundle's language; runtime `String(localized:)`
  values (the protection headline, the summary, the lock line) therefore stay
  English in that image. The XLIFF check owns Arabic completeness; a real
  in-app Arabic launch localizes those runtime values.
- **No policy change.** No lock rule, filter rule, consent sentence, allowance
  rule, partner path or commitment deadline changed in this pass.
- **The custom sidebar is not a native `List`.** It keeps the menu commands and
  the selected trait, but it does not implement arrow-key navigation between
  sidebar rows; `⌘1`–`⌘5` and the Go menu remain the keyboard route.
- **Not a measurement of ScreenZen.** The research is one window and one block
  page on one Mac. It is design vocabulary, not a claim about which product
  protects better.
